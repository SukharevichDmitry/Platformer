# Foundation polish plan for the first game

Assessment: 2026-10-14. Target: a complete **3–6 hour first game**, with the final length chosen after the movement, combat, and content workflow are stable. This is a code and asset audit plus an implementation plan. Passing automated checks establishes that tested invariants hold; it does not establish that movement feels good, combat reads clearly, or art is coherent.

## Player feedback pass — 2026-10-15

The developer reports that movement feels better, but passing through enemies is wrong, jumping does not reach visible platforms, and the first 5–10 seconds after Start stutter. Solid hero/enemy contact is restored. A 1.5-second sustained-contact regression found that an 80-density enemy still moved 0.63 tiles; the tuned heavier body passed the 0.05-tile displacement limit while the hero stayed blocked. This is a measured short-term Box2D contact rule, not a final decision about enemy knockback.

Jump speed is now 16.4 with a measured apex of roughly three tiles. Generated optional half-tile ledges and high bell/guarded-hall template ledges were moved into that reachable height band. The ruins profile is now version 3 because tile output changed. Existing version-2 saved ruins runs will be discarded by the versioned loader and regenerated; authored `start` remains unchanged. The 5,000-seed quality gate, profile/room checks, simulation, generated-location, persistence, packaged smoke, and camera checks passed. The reachability gate still guarantees the walking route; the new height check is a geometric bound, not proof that every platform approach is possible in play.

Normal gameplay previously constructed `WorldRenderer` with all debug geometry enabled. It is now disabled in `GameScreen`, removing a plausible rendering cost and visual clutter. Startup stutter has **not yet been proven fixed**: manually check first-frame and first-10-second frame pacing. If it persists, collect timing/profiling data before changing unrelated rendering code.

The game now emits one `STARTUP TIMING` line after ten seconds of play: construction time, worst frame, worst simulation update, worst render, and count of frames over 50 ms. This is diagnostic evidence for the next manual run, not a benchmark from the developer's machine. The full JDK 17 suite passed after adding it.

Second player-feedback pass: horizontal movement was too slow relative to the new jump, enemies retained push velocity, and the hero could not jump from an enemy's head. Hero walk speed is now 6.5 (with stronger ground/air acceleration and braking), regular-enemy chase speed 3.2, and boss chase speed 1.8. Idle/patrol states explicitly stop horizontal motion; enemy bodies also have linear damping for interrupted/paused AI. After each Box2D step, hero support is recomputed from terrain foot contacts plus touching hero/enemy body contacts whose manifold normal points upward under the hero. Head contact now supports jumping; side contact does not. Simulation regression covers a head landing and jump, a side contact in air, and absence of residual enemy drift after a push. `core:check`, 5,000-seed generation, simulation, generated-location, persistence, camera, and packaged smoke checks passed. This is automated behavior coverage; final movement/combat feel still requires a player check.

Jump-input follow-up: a new Space press is now buffered for 0.1 simulation seconds. A tap shortly before landing jumps on the first controller step after valid ground contact, including when the previous `JumpState` has not yet updated; a press made too early expires, and holding Space still cannot repeat the jump. The buffer is cleared on pause/hide through `clearInput`. Simulation regression covers a buffered tap and an expired held press. `core:check`, `lwjgl3:simulationRegressionTest`, and `lwjgl3:packagedSmokeTest` passed with JDK 17. This is input forgiveness, not network latency; coyote time for jumps *after leaving* an edge remains unimplemented and needs a separate feel decision.

Camera and navigation follow-up: horizontal camera follow and one-block-outside-location bounds remain unchanged; vertical camera motion now eases toward the hero at a frame-rate-independent rate and snaps to the new location on a transition. A top-right mini-map shows only rooms entered during this run, highlights the current room, and remembers discovery separately for each location when travelling away and back. Camera boundary and generated-location regressions cover smoothing, bounds, and room reveal. The mini-map is deliberately a compact room-layout view, not a tile-level map or a persisted save feature. Visible playtesting should tune its size/contrast and the vertical follow speed.

Location-entry presentation: a centered title now fades in for 0.4 seconds, holds for 2 seconds, then fades out for 0.8 seconds when play starts or the active location changes. Ordinary movement between rooms in the same location does not restart it. The current title is derived from the location ID (`start` → `Start`, `ruins` → `Ruins`); final narrative names and typography can be substituted without changing the timing rule. Simulation regression checks the fade phases and transition trigger; visual readability still needs a playtest.

## Working rule

Polish the small set of mechanics already in the game before expanding the world. Each change gets a measured baseline, one explicit gameplay rule, a focused regression check where behavior can break, and a short hands-on review. Keep the current libGDX 1.12.1, Box2D, JDK 17, and 1/60-second simulation. Finish or isolate the current uncommitted room and physics refactor before changing terrain fixtures; its location-wide fixture merging is directly involved in the half-tile defect.

The procedural ruins pipeline is technically complete, but its profile version 5 and 5,000-seed targets describe the **current implementation**. Any change to hero movement, tile collision, enemy body behavior, or attack reach requires rerunning the reachability, encounter, transition, and persistence gates. Revalidate tuning and bump the profile version when generation output or saved-run compatibility changes.

Vertical-room follow-up: every generated ruins layout now includes a watchtower above the bell hall. A narrow visible ladder supports Up/Down climbing, Left/Right movement on the shaft, and Space to jump away; its top stop clears the floor lip for a sideways exit. The route validator checks that the shaft remains clear at every generated size. The upper room appears on the mini-map only after entry. The 5,000-seed gate and desktop traversal test passed; visible playtesting should judge ladder readability, top exit feel, and combat balance in the upper room.

## Ordered work and exit gates

### 0. Establish the baseline and freeze geometry assumptions

- Save a short capture of walking, stopping, jumping, landing, pushing an enemy, crossing a half tile, and attacking while idle/moving/in air. Record frame times and world positions/velocities for the same inputs at 60 Hz; write down expected outcomes in plain language.
- Choose the gameplay unit rule: one tile = one world unit; identify the hero's collision box, sprite bounds, foot position, and intended maximum step, jump height, and gap width. Do not choose final constants based only on real-world gravity.
- Resolve the active room-runtime/merged-fixture work as a separate small change. Preserve its seam regression. Then start the geometry work with a known baseline.
- **Exit:** one repeatable test room and a baseline sheet for movement, collision, and attack. Existing prescribed checks still pass.

### 1. Make movement and contacts predictable

- Introduce a small hero movement configuration for ground acceleration, braking, air acceleration, jump velocity/height, gravity while rising/falling, maximum fall speed, and optional variable jump. Tune from observed arc and response; use the existing fixed step.
- Define jump input semantics: one jump per press, short input buffer and coyote time only if they improve control, clean landing transition, and no accidental repeat when Space is held. The current held-key condition can trigger another jump after `JumpState` returns to idle/move on landing.
- Choose the hero/enemy contact rule. Recommended starting rule: enemy bodies block terrain but do not physically shove the hero or one another; hero/enemy overlap is detected by a dedicated body/contact sensor, and attacks use separate directional hitboxes. Verify damage still works.
- Make grounding depend on valid supporting terrain (and explicitly supported platforms), not arbitrary actor overlap. Recheck it after teleports and room changes.
- **Exit:** recorded jump apex/height/airtime and stopping distance match chosen targets within a small tolerance; repeated input produces the same result at 30/60/120 render FPS; walking into an enemy does not roll it away; landing and transitions cannot leave the hero falsely grounded.

### 2. Rebuild the tile contract

- Define each tile with explicit type, visual region and draw rectangle, collision shape, support behavior, sight blocking, and whether it joins neighboring fixtures. Start with `_` as a full-width lower half block if it matches the intended design; reserve a separate symbol for any future one-way platform. Add top/side/bottom collision rules intentionally.
- Render geometry from the same tile definition used to build fixtures. Merge full solid cells across rooms; create separate partial fixtures for half tiles and avoid hidden full-cell collision. Update authored and generated room rows if the symbol meaning changes.
- Display a collision overlay in the test room and walk/jump against every side of full, half, and seam tiles. Update the generator's tile legality and reachability checks to match actual physics; avoid claiming vertical routes are verified until they are.
- **Exit:** visible edges align with Box2D fixtures to the chosen pixel tolerance; hero can stand on the intended half-tile top and pass through every intended empty area; there are no seam snags or invisible walls; authored and generated validation both pass.

### 3. Make the basic attack immediate and legible

- Specify one basic attack timeline in seconds or fixed ticks: input acceptance, startup, active hit window, recovery, cancel/buffer window, and animation frames. Start by targeting a visibly earlier hit than the current 0.3 s delay; tune with capture rather than hard-code a universal value.
- Activate only the intended facing hitbox during active frames. Track targets already hit by this swing and validate facing, range, alive state, and contact timing. Decide whether attacking can turn or move.
- Render the attack during walking and jumping according to an explicit priority or layered animation rule. Add temporary hit flash, sound cue, or small hit-stop only after timing is correct; later art can replace placeholders without changing combat logic.
- Give the existing enemy attack the same timeline model with a readable tell. Separate defeat from immediate body cleanup long enough to show feedback, without blocking room transitions.
- **Exit:** a press produces a visible response on the next simulation step; the hit occurs during the shown contact pose, strikes a target in front once, misses behind/out of range, and can be consistently avoided; press buffering and death/transition cases are covered.

### 4. Establish a small, repeatable art and audio pipeline

- Choose pixel art or another single visual direction, virtual resolution, pixels per world unit, palette, silhouette scale, animation pivot and naming/export rules. Identify which current files are original source and which are placeholders; keep an asset rights/source list.
- Make one final-quality hero idle/run/jump/attack set, one regular enemy, one full/half-tile set with corners and seams, and one short room treatment. Allow sprite dimensions to differ from collision boxes while keeping stable foot alignment.
- Add a minimal original/licensed sound pass for jump, land, swing, hit, enemy tell, damage, and UI. Check that sounds reinforce actual simulation events.
- **Exit:** one representative room can be played without debug overlays and every visible collision/attack has a readable visual and audio cue. Asset rebuilding is documented and reproducible.

### 5. Harden the foundation and then resume game design

- Add focused regression tests for jump/landing, hero/enemy contact, half-tile geometry and seams, hit timing/direction, damage cooldown, death cleanup, and render-state selection where feasible. Keep integration checks for transitions, persistence, and 5,000 generated seeds.
- Inspect screen sizes, camera framing, input after pause/focus loss, room load/unload, and performance with the largest current ruins seed. Remove noisy per-frame logging and dead geometry/attack helpers when their replacements are stable.
- After these gates, build a **10–15 minute mechanics proof** using existing rooms: traversal, one enemy encounter, a short generated route, and a return. Use it to decide which mechanics deserve content expansion. NPCs, dialogue, a broader playtest program, and Steam tasks follow that decision.
- **Exit:** prescribed automated checks are green, the hands-on checklist has no known movement/collision/combat blocker, and the mechanics proof is consistently replayable.

## Change checklist

For each milestone, run the narrow test first, then `core:check`, `lwjgl3:simulationRegressionTest`, and `lwjgl3:packagedSmokeTest`. For any movement, tile, spawn, or collision rule that affects ruins, also run `core:qualityGateGeneratedWorld`, `lwjgl3:generatedLocationTest`, and `lwjgl3:generatedRunPersistenceTest`; inspect the seed report and manually replay its shortest, longest, branched, and unbranched seeds. Run with JDK 17. Keep fixes small enough that a failed check points to one changed mechanic.
